# “我是怎么做的”素材

主窗口整理，都来自真实记录。本人筛选后上页面。

## 投入时间

- **本人实际操作约 2.5 小时。** 统计方法：取本人在各窗口发消息的时间，两条消息间隔超过 20 到 30 分钟算离开，算出 2.2 到 2.6 小时（统计到 2026-11-02 10:19，之后的修改要再加）。
- 页面时间轴只显示本人在操作的时段，空档折叠，并在折叠处写“离开 x 小时”。本人离开时，窗口可能还在跑。页面要写一句：“空档已折叠，完整记录见 CLAUDE.md。”
- 不写“总共只用 2 到 3 小时做完”这种容易被理解成日历时间的说法：提交记录从 11-01 16:29 开始，跨了一晚。写“实际操作约 2.5 小时”。

## 用了什么

- **模型：** 主要用 Claude Opus 5.5；截图拆解等子任务用 Claude Sonnet 5.5。
- **工具：** Claude Code 桌面版、多窗口、子 agent，GitHub Pages 部署。
- **窗口：** 主窗口（方向和范围、审核）、前端资源窗口、行业调研窗口、界面窗口。

## CLAUDE.md 怎么设计

它是全部窗口共用的项目记忆，也是交付材料的一部分。

- **工作规则：** 按指令一步步做；所有文件放进项目文件夹；公开仓库不放个人信息；完成前不替换线上首页。
- **如实标来源：** 判断记录分“本人定”和“Claude 提议”，做出来并验证过的才算亮点。
- **三张记录表：** 判断记录、可展示素材、交互记录，时间精确到分钟。
- **范围只有一个出处：** `方案/展示清单.md`。所有界面、亮点、不做的事都以它为准，避免多窗口各说各话。这条是两个窗口的范围出现冲突后才定下的。

## 每个窗口的提示词怎么设计

做法：本人定怎么分工、每个窗口负责什么，主窗口据此起草简报，本人可以随时改。每份简报都有同样的结构：

| 部分 | 作用 | 真实摘录 |
|---|---|---|
| 背景和前提 | 新窗口没有上下文，要交代够 | “范围已定稿，唯一依据是展示清单” |
| 明确产出 | 写到哪个文件，什么算完成 | “全部放在 `app/`，入口 `app/index.html`” |
| 限制用量 | 防止跑太久、额度用光 | “最多约 12 次搜索、10 次网页读取，边查边写文件” |
| 划清边界 | 多窗口共用文件夹时不互相覆盖 | “你只能创建和修改这 4 个文件，不要提交，不要切分支” |
| 证据规矩 | 防止 AI 编造 | “分清来源确认和我的推断，查不到就写查不到” |
| 验收方式 | 让窗口自己先验证 | “用无头 Chrome 走三条路径，确认每条都能解锁” |

不同窗口侧重不同：调研窗口强调来源和“找反面证据”；前端窗口强调许可证和体积；界面窗口强调内容和结构分开，方便后面改。

**踩过的坑也写进去：** 第一版简报写了相对路径，文件落到了错误的目录，之后一律写绝对路径。

## 其他能体现 AI 能力的点

| 点 | 真实例子 |
|---|---|
| 人做判断，AI 做执行 | 外卖和快递的责任差异、分批抢、AI 打码、平台担责都是本人提出的 |
| 敢否定 AI | 否定“骨架不依赖 scope”；打断子 agent 改开窗口；否定“全程两台手机”；砍掉运营看板 |
| 让 AI 找自己的反面证据 | 要求调研专门检验“信任优先”这个假设，结果它没被证实，方向随之调整 |
| 管理上下文 | 14 张竞品截图先由子 agent 转成结构化文件，主窗口只读结论，多轮讨论不被图片占满 |
| 按任务选模型 | 截图拆解用 Sonnet；界面先试 Sonnet，本人判断要换 Opus 高档后重做 |
| AI 审 AI | 主窗口用真实鼠标点击复核界面窗口的交付，退回 4 处；逐条核对页面参考链接都来自读过原文的来源 |
| 隐私意识 | 真实截图只留本地，先盖掉隐私再加示例文字，提交前检查仓库和历史记录 |
| 记录失败 | 路径写错、统计方法出错、窗口被删后消息没送达，都留在记录里 |
